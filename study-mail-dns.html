STUDY 05 · MAIL / DNS

회사 메일을 연결할 때
DNS에는 무엇을 설정해야 할까?

웹사이트가 열리는 것과 메일이 정상적으로 오가는 것은 별개의 문제입니다. 같은 도메인을 사용하더라도 메일은 MX, SPF, DKIM, DMARC 같은 별도 DNS 레코드를 통해 수신 서버와 발신 신뢰도를 관리합니다.

01 / SEPARATE ROUTES

같은 도메인을 써도 웹사이트와 이메일은 서로 다른 서버를 사용할 수 있습니다.

example.com 웹사이트는 GitHub Pages나 별도 호스팅을 사용하면서, info@example.com 메일은 Google Workspace나 Microsoft 365 같은 메일 서비스를 사용할 수 있습니다. 이때 웹 연결용 A·CNAME과 메일 연결용 MX·TXT 레코드는 서로 다른 역할을 합니다.

중요한 점

사이트 이전 때문에 네임서버를 바꿀 때 기존 메일 레코드를 빠뜨리면 웹은 정상인데 메일 수신이 끊기는 상황이 생길 수 있습니다.

02 / MX

MX 레코드는 이 도메인으로 들어오는 이메일을 어느 메일 서버가 받을지 지정합니다.

누군가 info@example.com으로 메일을 보내면 발신 서버는 example.com의 MX 레코드를 조회합니다. 거기에 지정된 메일 서버로 메시지를 전달합니다. 여러 MX가 있을 경우 우선순위 값에 따라 처리 순서가 결정됩니다.

  • 메일 서비스가 제공한 MX 값을 그대로 사용
  • 기존 MX 삭제 여부는 서비스 전환 계획에 맞춰 결정
  • 도메인 루트의 웹 A 레코드와는 별개로 관리

03 / SPF & DKIM

메일을 보낼 수 있는 서버와 실제 발신 메시지를 검증하는 장치가 필요합니다.

SPF

SPF는 이 도메인을 대신해 메일을 보낼 수 있는 서버 범위를 TXT 레코드로 선언하는 방식입니다. 여러 메일·마케팅 서비스를 사용한다면 하나의 SPF 정책 안에서 허용 범위를 정리해야 합니다.

DKIM

DKIM은 발신 서버가 메시지에 디지털 서명을 추가하고, 수신 측이 DNS에 공개된 키로 그 서명을 확인하는 방식입니다. 내용이 전송 중 변경되지 않았는지와 발신 서비스의 인증 여부를 판단하는 데 사용됩니다.

실무 주의

SPF TXT 레코드를 서비스마다 따로 여러 개 만드는 방식은 피하고, 사용 중인 발신 서비스를 한 정책으로 정리하는 것이 일반적입니다.

04 / DMARC

DMARC는 SPF와 DKIM 결과를 바탕으로 실패한 메일을 어떻게 처리할지 정책을 전달합니다.

DMARC를 통해 도메인 소유자는 인증 실패 메일을 모니터링만 할지, 스팸 처리하도록 요청할지, 거부하도록 요청할지 정책을 선언할 수 있습니다. 또한 보고서를 받을 주소를 지정해 도메인을 사용하는 발신 흐름을 점검할 수 있습니다.

  • 초기에는 모니터링 정책으로 현황 확인
  • 정상 발신 서비스의 SPF·DKIM 정리
  • 문제가 없는지 확인한 뒤 정책 강화 검토

DMARC를 강하게 설정하기 전에 현재 사용하는 뉴스레터, CRM, 문의폼, 외부 발송 서비스까지 함께 점검해야 합니다.

05 / MIGRATION CHECK

도메인이나 네임서버를 바꿀 때는 메일 DNS를 별도 체크리스트로 관리합니다.

반드시 백업할 항목

  • MX 레코드와 우선순위
  • SPF TXT 레코드
  • DKIM selector와 공개키
  • DMARC 정책
  • 도메인 소유권 인증용 TXT·CNAME
  • 메일 자동화·CRM이 사용하는 추가 레코드

변경 후에는 내부 메일끼리만 테스트하지 말고 외부 서비스에서 수신·발신을 각각 확인하는 편이 좋습니다. 스팸함 유입 여부와 발신 인증 결과도 함께 확인합니다.

SOST의 기준

DNS 변경 전 전체 레코드를 캡처·백업하고, 웹 연결과 메일 연결을 별도 항목으로 나눠 확인합니다. 메일이 운영 중인 도메인은 네임서버를 단순 교체하지 않습니다.
