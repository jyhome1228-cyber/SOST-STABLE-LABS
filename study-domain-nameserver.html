STUDY 04 · DOMAIN / DNS

도메인과 네임서버는
어떻게 연결되는가?

도메인을 구입한 곳, DNS를 관리하는 곳, 실제 웹사이트가 올라간 서버는 서로 다를 수 있습니다. 이 세 가지 역할을 분리해서 보면 사이트 이전과 도메인 연결이 훨씬 명확해집니다.

01 / REGISTRAR

도메인을 구입한 곳은 주소의 소유권을 관리하는 곳입니다.

가비아, 후이즈, Cloudflare Registrar 같은 등록기관은 도메인 등록과 갱신, 소유자 정보를 관리합니다. 하지만 도메인을 어디에서 샀는지가 웹사이트가 어디에 올라가 있는지를 의미하지는 않습니다.

도메인은 하나의 주소이고, 실제 서비스 위치는 DNS 설정을 통해 따로 연결됩니다.

02 / NAMESERVER

네임서버는 이 도메인의 DNS 정보를 어디에서 물어봐야 하는지를 지정합니다.

브라우저가 example.com의 위치를 찾으려면 먼저 이 도메인의 DNS를 관리하는 네임서버를 확인합니다. 네임서버를 바꾼다는 것은 DNS 관리 주체 자체를 다른 서비스로 옮기는 것에 가깝습니다.

중요한 구분

네임서버 변경은 A 레코드 한 줄을 바꾸는 것보다 영향 범위가 큽니다. 기존 DNS 레코드를 새 네임서버 쪽에 먼저 복사하지 않으면 웹이나 메일 설정이 함께 끊길 수 있습니다.

03 / DNS RECORDS

실제 웹사이트 연결은 A, AAAA, CNAME 같은 DNS 레코드로 결정됩니다.

  • A: 도메인을 IPv4 주소에 연결
  • AAAA: 도메인을 IPv6 주소에 연결
  • CNAME: 한 호스트 이름을 다른 호스트 이름에 연결
  • MX: 메일을 받을 서버 지정
  • TXT: SPF, DKIM 검증값 등 문자열 정보 저장

예를 들어 www.example.com은 CNAME으로 특정 호스팅 주소를 가리키고, 루트 example.com은 A 레코드로 서버 IP를 가리키는 식으로 구성할 수 있습니다.

04 / PROPAGATION

DNS 변경은 저장 즉시 전 세계에 동시에 반영되는 구조가 아닙니다.

DNS 응답은 여러 리졸버와 네트워크 구간에서 캐시됩니다. TTL은 해당 응답을 얼마나 오래 캐시할지에 대한 기준 중 하나입니다. 그래서 레코드를 바꾼 직후 사용자마다 예전 서버와 새 서버가 다르게 보이는 시간이 생길 수 있습니다.

중요한 이전 작업이라면 변경 전에 TTL을 낮추고, 새 서버가 준비된 상태에서 레코드를 전환하는 방식이 안전합니다.

05 / MIGRATION

사이트 이전은 웹 레코드만 보지 말고 기존 DNS 전체를 백업한 뒤 진행합니다.

변경 전에 확인할 것

  • 현재 네임서버가 어디인지
  • A, CNAME, MX, TXT 레코드 전체
  • 메일이 같은 도메인을 사용하는지
  • 서브도메인과 인증용 레코드가 있는지
  • 새 호스팅이 요구하는 정확한 값
  • SSL 발급이 DNS 변경 후 정상적으로 진행되는지
SOST의 기준

도메인 이전과 사이트 이전을 같은 작업으로 보지 않습니다. 소유권, DNS 관리, 웹 호스팅과 메일을 각각 분리해 체크한 뒤 필요한 부분만 변경합니다.
